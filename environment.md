# Environment

Part of the plan(./PLAN.md) -- runtimes, versions, required env vars, and local setup steps.

- **Python**: 3.13.4, in a project-local `.venv` (`requires-python = ">=3.11"` in `pyproject.toml`).
- **Runtime dependencies** (exact-pinned in `pyproject.toml`):
  `pydantic-ai==2.48.0`, `openai==3.19.0`, `httpx==0.28.1`, `lancedb==0.39.0`, `sentence-transformers==6.1.0`, `datasets==5.0.1`, `pandas==3.0.6`, `loguru==0.7.3`, `statsmodels==0.15.0`, `matplotlib==3.11.2`, `pyyaml==6.0.3`, `rank-bm25==0.2.2`, `python-dotenv==1.2.3`.
  `sentence-transformers` pulls in `torch==2.14.0` and `transformers==5.17.0` transitively (CPU/MPS only — no CUDA, no `bitsandbytes`, no local model loading of the LLMs under test).
- **Dev dependencies**: `pytest==9.1.1`, `pytest-asyncio==1.4.0` (installed via the `[dev]` extra, never separately).
- **Running tests**: `.venv/bin/pytest` from the repo root (`testpaths = ["tests"]`, `asyncio_mode = "auto"` are set in `pyproject.toml`, so no extra flags are needed). One test is marked `live` and hits the real endpoint; it skips unless `MEDICAL_RAG_LIVE_TESTS=1` is set alongside the sourced `.env` (`set -a; source .env; set +a; MEDICAL_RAG_LIVE_TESTS=1 .venv/bin/pytest`). Excluded from ordinary runs by `.venv/bin/pytest -m "not live"`.
- **Running the pipeline end to end** (current state — retrieval only):
  1. `.venv/bin/python scripts/build_index.py --corpus statpearls` — idempotent; downloads/caches the StatPearls corpus under `data/statpearls/` on first run (~1.9GB from NCBI, one-time), then embeds it and writes a LanceDB table to `data/index/statpearls/`. Pass `--force` to rebuild.
  2. `.venv/bin/python -m medical_rag.eval.judge --stats` — what the oracle can currently answer, and under which rubric sha. Run it before anything that judges; it is the cheapest way to find out whether a run would cost endpoint time or nothing.
  3. `.venv/bin/python scripts/eval_retrieval.py` — score frozen strategies against the cached verdicts, **zero completions and no endpoint at all**; `--strategy`/`--ks`/`--require-coverage` on the same line. This is the command PLAN.md's rules point at.
  4. `.venv/bin/python scripts/run_retrieval_grid.py` — the grid: retrieve all five strategies, judge the *union* of their candidates (this is what spends endpoint time), write a run bundle and re-render a findings file. `--dry-run` prints the plan and its cost; `--rerender <run>` rebuilds a findings file from a bundle already on disk for free, which is the gate a refactor of this code has to pass.
  5. `.venv/bin/python scripts/inspect_retrieval.py --serve` — the interactive surface, for deciding what to change next.
  6. The old generator-side commands are gone with their study (ADR-0007): there is no `run_pilot.py` or `run_experiment.py`, and no condition set to freeze. Phase 5–6's exploratory scripts still run (`scripts/exploration/closed_book.py --sample-size 20`, `raw_rag.py`) and are the only readers of `model_a`/`model_b`; their rows and chains land in gitignored `outputs/exploration/<phase>/<stamp>/`, their distilled findings in the frozen tracked `experiments/phase*/FINDINGS.md`.
- **LLM endpoint**: `model_a` and `model_b` in `config/models.yaml` both point at **one** locally served, OpenAI-compatible **oMLX** instance (`omlx-server`) at `http://localhost:8080/v1` — `model_a` = `Qwen2.5-7B-Instruct-8bit`, `model_b` = `DeepSeek-R1-Distill-Qwen-7B-8bit`. `api_model_name` must be exactly the id `GET /v1/models` advertises (the bare name, **not** a filesystem path — a path comes back `HTTP 404 Model ... not found`, which `closed_book.py`'s preflight catches before firing). Earlier setups used two `mlx_lm.server` instances on `:8081`/`:8082`; those are gone, and since one process now serves both arms they share a GPU — run them sequentially, not with `--concurrent-models`, or per-arm tok/s is confounded. **The server also applies per-model sampling the client never sends**: `top_k`, `top_p` and `repetition_penalty`, and for `model_b` `enable_thinking` plus a 4,096-token thinking budget — the constraint that makes `model_b` terminate at all (`experiments/phase5/FINDINGS.md` §8). Those live in `~/.omlx/model_settings.json`, outside git, so a run's `context.md` must record them (`closed_book.py --note`) and R6's freeze must name them or the frozen config is not reproducible. The judge is served by the same process, so its sampling settings are ground truth's settings too (ADR-0008) — record them for grid runs as well. API keys live in the repo-root `.env` (gitignored; template in `.env.example`) as `MODEL_A_API_KEY` / `MODEL_B_API_KEY` / `JUDGE_MODEL_API_KEY` and are read through `ModelConfig.api_key_env`. `config.load_env()` merges that file into `os.environ` during `load_config()`, so the `set -a; source .env; set +a` prefix is optional for the Python entry points (fill-only: an exported value wins, and an empty `KEY=` is skipped so `LLMClient` still raises `LLMError` naming the variable rather than sending a key that would 401). Keep the prefix for raw `curl` probes.
- **Endpoint behaviour** (drove implementation choices in Phase 4 — evidence in `experiments/phase4/FINDINGS.md`): `model_b` is a *reasoning* model whose chain of thought arrives in a non-standard field with the graded answer in `content`; at a small token budget `content` can come back absent with `finish_reason="length"` (hence `max_new_tokens: 1024` and `LLMClient` raising `LLMError` on empty content with no reasoning to recover from). The field is named `reasoning` on the old `mlx_lm.server` instances and `reasoning_content` under oMLX, so `_extract_reasoning()` (`llm.py`) accepts either name and checks `model_extra` as well as attributes. The endpoints accept `max_completion_tokens`, `temperature` and `top_p` without complaint (`seed` was accepted but ignored — it is inert, and no longer sent; see `experiments/phase5/FINDINGS.md` §"Resolution"). Tool calling is unreliable (`tool_choice="required"` produced no tool call), while native JSON mode works — so `agenerate_structured()` uses pydantic-ai `PromptedOutput` (JSON in `content`) rather than tool calling.
- **Why `BAAI/bge-small-en-v1.5`**: the embedding model specified in the original design — a small, fast, retrieval-tuned model that supports an asymmetric query/passage convention (`retrieval/embedder.py`'s `BGE_QUERY_INSTRUCTION` prepends `Represent this sentence for searching relevant passages: ` -- trailing space included -- to queries and nothing to passages), which the codebase implements explicitly.
- **Why `cross-encoder/ms-marco-MiniLM-L-6-v2`**: the reranker specified in the original design — a standard, general-purpose passage-relevance cross-encoder, applied to the top-`k` candidates the retriever returns when `config.retrieval.strategy` names a `*_rerank` strategy (`retrieval/strategy.py` + `retrieval/reranker.py`) — reranking is a lever, not an unconditional step. The first grid found the funnel's ceiling is the one hard number in this repo: `top_k_rerank: 5` caps every `*_rerank` cell at 5, which is why dense_rerank's 45/45/45 is an artefact and not a plateau.
- **Device selection note**: on this machine, `torch`'s CPU backend produces NaN output from the cross-encoder's forward pass (confirmed by inspecting intermediate hidden states); MPS does not. `Embedder`'s default device order is therefore `cuda` > `mps` > `cpu`, and both the embedding model and the reranker (which shares the embedder's device) run on MPS here.
