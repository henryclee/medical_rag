# Medical RAG Experiment — Project Plan

## Context

This project is a reproducible pipeline for running retrieval-augmented generation (RAG) experiments on medical board-exam questions (MedQA-USMLE): it can evaluate how interventions — retrieval, reranking, query reformulation, and answer verification — affect accuracy, and whether that effect depends on which LLM is answering. The pipeline itself is the artifact; the current study (built around these levers) is one instantiation of it. Which levers are active and what the condition set looks like are provisional until the design freeze (Phase 10). Generation is never local: every model is served remotely behind an OpenAI-compatible endpoint, and the pipeline only ever makes HTTP calls to it. Retrieval runs against StatPearls, a clinical reference corpus, embedded and indexed once and then queried repeatedly across the experiment.

As of this document, the project is a pip-installable `src`-layout package (`medical_rag`) with a working configuration layer, both data loaders, and a fully functional retrieval subsystem — including a real, populated vector index built from the actual StatPearls corpus. Everything from query reformulation and answer verification through the experiment runner, statistics, and report generation is still a stub. The end state is a repo where `python scripts/build_index.py` and `python scripts/run_experiment.py` reproduce the study from scratch, producing `outputs/runs/summary.csv`, `outputs/runs/summary.json`, figures under `outputs/figures/`, and a `RESULTS.md` reporting effect sizes and confidence intervals for the contrasts actually run.

The experiment design described above — the condition set, prompt wording, `min_chunks`, the reformulator's retry policy, and the primary significance test — is provisional. Phases 4-9 exist to explore and pressure-test that design, running against a held-out dev split rather than the test split. A design freeze (Phase 10) follows Phase 9: the design is finalized there, before the confirmatory run against the test split in Phase 13. Because that exploration is where the interesting failures are, Phases 5–9 keep their scripts and evidence rather than discarding them — see the exploratory-artifact convention below.

## Phases

Phases 4-9 are exploratory. The `🔲 planned` interfaces in `interfaces.md` for the modules those phases touch are provisional and may change based on what those phases find.

**The exploratory-artifact convention.** An exploratory phase is not finished when its check passes; it is finished when its evidence is reviewable — “why did `model_b` get this one wrong?” is a question asked later, at the Phase 10 freeze, by which time the config that produced the answer may already have been edited. So every phase from 5 to 9 leaves three artifacts behind:

1. **A tracked, re-runnable script** under `scripts/exploration/` — not a REPL session, and not a throwaway deleted afterwards. It pins its question sample (`--sample-size` / `--sample-seed`) and logs the `question_id`s it selected, otherwise Phase 6 cannot honestly say “the same 20 questions”.
2. **A raw run directory** under `outputs/exploration/<phase>/<UTC-stamp>/` (gitignored, regenerable): `results.jsonl` (one row per question × model), `chains/<model>__<question_id>.md` (the chain of thought — the answer line alone rarely shows why a reasoning model went wrong), and `context.md` (git rev, resolved config, `api_model`/endpoint per arm, the sampled `question_id`s).
3. **A findings entry** in tracked `experiments/<phase>/FINDINGS.md`: the numbers, the questions that failed *with the chain that shows why*, the decision each produced, and any Open questions item it settled or moved. This is the only one of the three that survives a `--force` rebuild or a new machine, and it is what Phase 10 reads.

Rows keep the `QuestionResult` field shape (`interfaces.md`) so Phase 12's `classify_failure()` can read exploratory data without a translation layer, and every row carries the `params` / resolved `min_chunks` / `max_retries` active for it inline (Open questions, item 9), so a log stays self-describing after `conditions.yaml` moves on.

Keep **every** chain, not just the wrong ones: `model_b`'s chains run 2.9k–4.8k characters, so a 20-question × 2-model phase is ~200 KB — cheap — and failures-only retention hides the base rate. The shared writer lives in `scripts/exploration/_common.py` during exploration and is promoted into `experiment/runner.py` at Phase 9 if it earns it, so the study does not end up with two logging systems.

Two guardrails: exploratory artifacts are dev-split only and never land in `outputs/runs/`; and an n=20 phase is reported as plumbing evidence, never cited in `RESULTS.md` — the discipline Phase 4 applied to its own notes.

**Phase 1 — Scaffold.** The project is a `src`-layout, pip-installable package (`pip install -e ".[dev]"`) named `medical_rag`, with a subpackage per pipeline stage (`data`, `retrieval`, `modules`, `generation`, `experiment`, `analysis`) and top-level `config/`, `scripts/`, `tests/`, gitignored `data/` and `outputs/`. `pyproject.toml` declares exact-pinned runtime and dev dependencies and configures pytest. A smoke test (`tests/test_pipeline.py`) confirms the package imports and exposes `__version__`.

**COMPLETED**

**Phase 2 — Configuration and data loading.** `medical_rag.config.load_config()` loads and validates three YAML files (`config/default.yaml`, `models.yaml`, `conditions.yaml`) into a single `ExperimentConfig`, failing loudly if any condition references an undefined model. `load_medqa()` loads the 1,273-question MedQA-USMLE test set from Hugging Face (`GBaker/MedQA-USMLE-4-options`) into typed `MedQAQuestion` records. `load_statpearls()` builds the StatPearls corpus directly from its authoritative source — NCBI's raw NLM-XML archive plus a vendored, faithful port of MedRAG's own chunking algorithm — rather than relying on the official (empty) `MedRAG/statpearls` Hugging Face repo or unverified community mirrors, and caches the result locally after the first (~1.9GB) build.

**COMPLETED**

**Phase 3 — Retrieval.** `Embedder` wraps `BAAI/bge-small-en-v1.5` with BGE's asymmetric query/passage convention (an instruction prefix on queries only). `medical_rag.retrieval.index` builds and loads an exact-search LanceDB vector table. `Retriever` combines the two, plus a `cross-encoder/ms-marco-MiniLM-L-6-v2` reranker, into `retrieve()` + `rerank()`. `scripts/build_index.py` drives the whole load → embed → index → save pipeline from the command line. A real index exists on disk at `data/index/statpearls/`: 380,454 chunks from 9,652 StatPearls articles (NCBI's live corpus has grown since MedRAG's 301,202-snippet paper snapshot), embedded and indexed, manually verified against real MedQA questions to return topically relevant results.

Items 3-6 and 8 are decisions to make at the design freeze (Phase 10), not blockers before Phase 13. Item 2, the degenerate model factor, has been resolved. **Phase 5 is complete (run `20260928T020841Z`): item 13, the `model_b` non-termination it discovered, is resolved by an endpoint-side thinking budget, and both arms are measured** — the unblocked next step is Phase 6, reusing Phase 5's pinned 20 questions. 1. ~~**Real model endpoints.**~~ **RESOLVED (Phase 4).** `config/models.yaml` points at two local `mlx_lm.server` endpoints (see `environment.md` for the current addresses/keys); `LLMClient.agenerate()`/`agenerate_structured()` verified live — `experiments/phase4/FINDINGS.md`.
2. ~~**What "two models" means — and it is now blocking.**~~ **RESOLVED.** `models.yaml` names an instruct/reasoning pair (`model_a`/`model_b`), verified live — `experiments/phase4/FINDINGS.md`. Still open as a Phase 10 question: whether instruct-vs-reasoning is the axis the study actually wants, rather than two capability tiers of one family.
3. **Reformulator retry policy.** How many validation retries before falling back to the original question, and should that fallback count toward any per-run failure-rate metric?
4. **Resume/checkpoint mechanism.** `ExperimentRunner.run_condition()` needs to skip already-logged `(condition, question_id)` pairs on restart — worth deciding now whether that's done by re-reading the existing JSONL file's question ids at startup (simple, but O(n) reread each restart) or a separate lightweight manifest/index file.
5. **Primary significance test.** Phase 2's design review recommended replacing the original spec's four-method statistics stack (bootstrap CI + paired t-test + McNemar + factorial ANOVA) with one primary method plus bootstrap CIs as secondary presentation, tentatively McNemar's test. Worth confirming McNemar (simple, pairwise, matches binary per-question outcomes) over a mixed-effects logistic regression (handles the full factorial and question-level random effects in one model, but heavier to implement and explain) before Phase 11.
6. **Failure taxonomy scope.** The original spec calls for "a combination of heuristics and manual review" with a CLI to export a sample for manual labeling. Worth deciding whether manual labeling is in scope for this codebase at all, or whether `analysis/failure_taxonomy.py` should ship heuristics-only and treat manual review as an out-of-band step the user does separately. Decide against the chains already collected in `experiments/phase*/`: if the exploratory failures sort cleanly into the seven `FailureCategory` values, heuristics-only is defensible; if not, that is the argument for a labeling pass.
7. **StatPearls corpus size drift.** The built corpus has 380,454 snippets vs. MedRAG's documented 301,202 (NCBI's live Bookshelf archive has grown since their paper snapshot). Worth deciding whether `RESULTS.md`/`README.md` should note this explicitly as a caveat against direct comparison to MedRAG's published numbers.
8. **Sampling temperature.** **`model_a`'s temperature/top_p RESOLVED:** set to `0.7`/`0.8`, Qwen2.5-7B-Instruct's own published `generation_config.json` defaults, replacing the placeholder `0.9` carried over from the original spec's example. That same config also recommends `top_k=20` and `repetition_penalty=1.05`, but neither is wired through `ModelConfig`/`LLMClient` yet (only `temperature`/`top_p`/`max_new_tokens` are sent) — adding them is a small follow-up (an `extra_body` passthrough, same shape as the thinking-mode kwarg), not a config edit, and is not scheduled to a phase. `model_b`'s `0.6`/`0.95` are already DeepSeek-R1-Distill's own recommended settings, not a placeholder — nothing to confirm there. Still open: `max_new_tokens` sizing — **half settled by Phase 5.** `model_a` keeps **1,024** (0/20 `finish_reason="length"`, worst case 475 tokens = 46% of budget, median 352). `model_b`'s 16,384 is **not validated**: 2 of its 3 completions spent the entire budget and emitted no answer text at all, so its sizing is blocked on item 13 rather than on measuring a bigger number (`experiments/phase5/FINDINGS.md` §2/§4).
9. **`QuestionResult` doesn't snapshot active params.** `QuestionResult` (`interfaces.md`) has no field echoing which `params` (or resolved `min_chunks`/`max_retries`) were active for that logged row — analysis has to join back against `conditions.yaml` by `condition_id`, which is only reliable if `conditions.yaml` is never edited after a run that produced already-logged results. Worth deciding at Phase 9 whether `QuestionResult` should snapshot these values directly for a self-contained, tamper-proof log record. The convention already requires exploratory rows to snapshot active params inline; Phase 9 should carry that into `QuestionResult` rather than decide it fresh. **Phase 5 produced the counterexample that proves the rule:** its 17 `model_b` connection-error rows carry only 13 fields — `_common.py`'s `error_row()` drops `params`, `finish_reason`, token counts and prompt size — so those rows are not self-describing and cannot be told apart from error rows produced under different settings. Whatever Phase 9 adopts, the rule must cover error rows too, not just completed ones (`experiments/phase5/FINDINGS.md` §5).
10. ~~**Does `seed` actually change anything?**~~ **RESOLVED — `seed` removed from the pipeline entirely.** Phase 5 measured `seed` as inert on the `model_a` endpoint: same prompt at `temperature=0.7` > 0, two draws at `seed=0` and two at `seed=100/101` produced five byte-identical outputs (chain-body sha256 identical across all five, differing only in the header stamp) — `experiments/phase5/FINDINGS.md` §3/§5. Rather than pursue the same measurement on `model_b` (whose endpoint died mid-check) or replace fixed seeds with a different repeated-draws mechanism, the decision is to drop the repeated-draws design outright: `ModelConfig.seed`, `ConditionConfig.seeds`, the `seed` parameter on `LLMClient.agenerate`/`agenerate_structured`, and `QuestionResult.seed` are all removed (not deprecated or defaulted to `None`), and the experiment runs **one completion per question per condition** instead of three per seed. This also removes the `mlx_lm.server` batching penalty Phase 4 found from passing `seed` (`experiments/phase4/FINDINGS.md` §5) — see item 12.
11. ~~**Thinking mode.**~~ **RESOLVED — no toggle.** `extra_body={"chat_template_kwargs": {"thinking": False}}` is accepted by `model_b` and measurably faster (`experiments/phase4/FINDINGS.md` §4), but `chat_template_kwargs.thinking` is a Qwen3-style hybrid-reasoning template feature; `model_a` (Qwen2.5-7B-Instruct) has no thinking mode to toggle, so an on/off comparison would be symmetric for `model_b` only and would either no-op or behave unpredictably for `model_a` — not the clean per-model factor Phase 5 would need to report it. Rather than run an asymmetric toggle across the two models, thinking mode stays fixed on (its default, and Phase 4's already-live configuration) for both models in every condition. No Phase 5 measurement and no `ModelConfig` field are needed for this.
12. **Concurrency in the Phase 9 runner.** At ~15–45 s per answer and ~25 tok/s, the Phase 13 run (1,273 questions × the frozen condition set) is days of wall-clock time if questions are awaited one at a time. Phase 4 found that passing `seed` disables `mlx_lm.server`'s batching (`experiments/phase4/FINDINGS.md` §5); now that `seed` is never sent (item 10), that constraint no longer applies, and Phase 9's concurrency sweep should be re-measured without it — a semaphore over one endpoint may unlock real parallel compute rather than merely hiding network/queueing overhead. `model_a` and `model_b` are already on separate endpoints, so those two run concurrently with each other for free. `ExperimentRunner` needs explicit async concurrency control — an `asyncio.Semaphore` **per model endpoint** (not global) plus per-request timeout handling. Fold the measurement into Phase 9 rather than a separate exploratory phase: run Phase 9's pilot at per-endpoint concurrency 1/2/4, record wall-clock and any throughput collapse in `experiments/phase9/FINDINGS.md`, and freeze the chosen ceiling at Phase 10 alongside the other frozen parameters. Keep it configurable so a run's degree of parallelism is reproducible.

The three sub-problems resolved unevenly, and that asymmetry is the residue to carry: **(a) solved, but outside git** — the committing constraint is server-side, so the `extra_body` passthrough is no longer needed to make `model_b` terminate; it is now needed for *reproducibility*, because no artifact in this repo names the parameters that decide whether the model answers at all. **(b) NOT solved** — recovery fired 0/40 rows, so `_recover_answer`'s loop replay is unexercised rather than fixed. **(c) solved and tested** — `EndpointCircuitBreaker` (3 consecutive transport failures ⇒ abandon the arm) plus the `completed_keys()` fix that plain `--resume` depends on. Original analysis follows, kept as the record of how the failure presented. Found by running Phase 5, not by guessing: 2 of the 3 `model_b` completions that ran fell into a repetition attractor — 1,034 and 349 occurrences of "Alternatively" in [`experiments/phase5/chains/model_b__1312.md`](experiments/phase5/chains/model_b__1312.md) and [`model_b__2391.md`](experiments/phase5/chains/model_b__2391.md) — consuming all 16,384 tokens (~4.5 min each) and returning `content_chars=0`: no answer text, only chain of thought. The 3rd completion was 626 tokens and 9.9 s, so this is not "the model thinks long"; it is a distinct failure mode, and the phase's per-model accuracy comparison is unusable because of it. Three things follow, and they are separate problems: **(a) the model needs a decoding constraint that makes it commit.** `mlx_lm.server` accepts per-request `repetition_penalty`, `presence_penalty`, `frequency_penalty`, `top_k`, `min_p`, `xtc_probability` and `stop` (`server.py:1174-1192`) and defaults `repetition_penalty` to 0.0 — off — while `LLMClient._complete()` sends only `max_completion_tokens`/`temperature`/`top_p`. The `extra_body` passthrough item 8 already named as an unscheduled follow-up is now the critical path: add it, then sweep penalty × ceiling on the pinned sample. **Raising `max_new_tokens` is not the fix** — a 32K ceiling buys 4.5 more minutes of the same loop. **(b) the recovery path makes it worse.** `_recover_answer` (`llm.py:297-328`) replays the abandoned chain as the model's own prior turn, so a loop gets fed back to itself with 512 more tokens; it went 0/2 here and worked in Phase 4 only because those chains were budget-starved rather than degenerate. It needs to detect a loop (`content_chars == 0` plus a repetitive tail) and re-prompt from the question, or mark the row unrecoverable and stop paying. **(c) the runner must stop when an endpoint dies.** The `model_b` server on `:8082` died under an in-flight request (one 224 s hang), and the script walked its remaining 16 questions in 7 s of refusals, exiting `1` with no traceback. Needs N-consecutive-`APIConnectionError` ⇒ abort that model arm loudly. Also fix `completed_keys()` (`_common.py:217-220`), which counts error rows as done and therefore makes plain `--resume` skip exactly the questions that need retrying — Phase 13's resumability claim rests on the same rule. Phases 6-9 can proceed against `model_a`, but Phase 5's `model_b` half, item 8's `model_b` half, and the model-vs-model contrast all wait on this one.
